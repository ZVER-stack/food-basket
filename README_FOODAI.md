# FoodAI первый агент и общий бот

Реализована часть участника 1 по ТЗ 00 и 01. Пользователь вводит свой московский адрес или отправляет геопозицию; приложение определяет одну из десяти зон по полигону. Затем пользователь открывает «Где купить дешевле?», отправляет список и получает сравнение полных корзин с SKU, фасовками, целыми упаковками и датами выгрузки. После уточнения пересчитываются выбранные позиции. Три других раздела работают как заглушки для модулей команды.

## Установка и проверка без ключей

Python 3.11+. Команды выполняются из корня репозитория.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m foodai.demo --query "молоко 1 л, яйца 10 шт" --followup "Замени молоко на безлактозное" --trace data/demo_trace.json
```

`LLM_MODE=mock` использует детерминированный тестовый драйвер. Он вызывает тот же интерфейс инструментов и показывает искусственные цены. Проверка выбора действий реальной моделью выполняется отдельно в режиме Groq. Локальный журнал `data/demo_trace.json` содержит названия вызванных инструментов, аргументы и результаты.

## Telegram и Groq

В локальном `.env` задайте `BOT_TOKEN` от BotFather, `GROQ_API_KEY` и `LLM_MODE=groq`. Токены остаются на вашем компьютере. Для проверки только Telegram с тестовыми данными можно оставить `LLM_MODE=mock`.

```powershell
.\.venv\Scripts\python.exe -m foodai.main
```

Поддерживаются `/start`, `/menu`, `/help`, кнопки четырёх разделов, «Назад», «Главное меню», «Изменить адрес» и отправка геопозиции. После первого указания зона сохраняется в SQLite и восстанавливается после перезапуска. При смене адреса выбранная корзина сбрасывается. Диалоги пользователей изолированы.

Модель и базовый URL настраиваются через `MODEL_NAME` и `GROQ_BASE_URL`. По умолчанию используются `openai/gpt-oss-120b` и `https://api.groq.com/openai/v1`. За запрос разрешено до восьми вызовов локальных инструментов. Доступные действия ограничены текущим этапом: требования, поиск, расчёт. После поиска модель не меняет требуемые количества под фасовки; готовые корзины сравниваются приложением без дополнительных обращений к модели. Повторы HTTP 429/5xx и сетевых ошибок ограничены тремя попытками. Тексты карточек передаются как данные, произвольный код и SQL из ответов модели не выполняются.

Реальный запуск Telegram и Groq требует ваших ключей. Офлайн-тесты вызывают aiogram Dispatcher через `feed_update` с подменённой транспортной сессией. Скриншоты живого Telegram и журнал живой модели появятся после такого запуска.

## Десять зон

Поддерживаются `msk_center`, `msk_01`–`msk_09`. Старые 197 H3-зон в приложение не импортируются.

Пользователь вводит свой адрес. Задайте ZONES_PATH и GEOJSON_PATH из набора десяти зон: локальный справочник и Photon находят дом, а полигон определяет зону. Неоднозначные и находящиеся вне покрытия адреса не назначаются ближайшей зоне. Каталог зоны не подтверждает доставку в каждый дом.

Файлы с личными адресами, координатами, реальными каталогами и пользовательской SQLite размещайте в `data/`, который исключён из Git. Точный адрес пользователя в Groq не передаётся. Для запуска агента нужны только идентификатор зоны и разрешённые витрины.

## Реальный каталог Ozon

Импорт читает сохранённую SQLite локально. Укажите путь к собранному снимку десяти зон.

```powershell
.\.venv\Scripts\python.exe -m foodai.import_catalog --source "C:\data\ozon_10_zones\snapshot" --output data/ozon.json
.\.venv\Scripts\python.exe -m foodai.demo --catalog data/ozon.json --query "молоко 1 л, яйца 10 шт" --trace data/ozon_trace.json
```

Для бота установите `CATALOG_PATH=data/ozon.json`. Импорт по умолчанию использует обычную цену упаковки. Предложения с неподтверждённой перенесённой ценой, неизвестной фасовкой или датой исключаются; импорт показывает число отклонённых записей. Цена по карте включается только отдельным импортом с `--price-mode card`, если пользователь согласен покупать по карте. Смешивание разных режимов цены при дополнении каталога запрещено.

В выгрузке Ozon от 21 ноября проверено 64 843 строки по десяти зонам. В приложение импортировано 36 946 предложений с пригодной фасовкой и подтверждённой обычной ценой; 27 897 отклонены при проверке. Исходная выгрузка сохраняется отдельно. Наличие и цены показываются с датой снимка, доставка в сумму не входит.

Для остальных сервисов есть общий формат `Product` и импорт CSV по 37-колоночному шаблону куратора. В строках обязательны `service`, `zone_id`, `product_id`, `name`, `price`, `amount`, `parsed_at`; `in_stock` должно быть явно `true`, чтобы товар участвовал в поиске. Добавление второй сети:

```powershell
.\.venv\Scripts\python.exe -m foodai.import_catalog --format csv --source data/samokat.csv --output data/catalog.json
.\.venv\Scripts\python.exe -m foodai.import_catalog --format csv --source data/vkusvill.csv --output data/catalog.json --append
```

Готовый объединённый JSON указывается в `CATALOG_PATH`. Лавка и Большая Лавка должны иметь разные `storefront_id` в каноническом JSON. Импорт общего CSV использует `service:store_id`, если ID склада известен, иначе отдельный ключ `service:address:zone_id`. Этот ключ не означает установленный ID склада. Если один склад имеет две витрины, поставщик адаптера должен явно разнести их по разным `storefront_id` до объединения.

Реальные выгрузки остальных трёх сервисов в десяти новых зонах здесь ещё не подключены. В `fixtures/catalog.json` есть искусственные предложения всех четырёх сетей и отдельная Большая Лавка во всех десяти зонах. Они применяются только для разработки и тестов.

## Контракт для команды

```python
async def run(user_text: str, context: dict) -> AgentResult:
    ...
```

`AgentResult` содержит `text`, `status`, `structured`, `buttons`. Допустимые статусы `ok`, `partial`, `no_data`, `need_clarification`, `error`. Telegram также принимает словарь с этими полями. `context` передаёт `zone_id`, ограниченную историю и структурированное состояние корзины. Зарегистрируйте готовый модуль в `foodai/bootstrap.py` под ключом `meal_plan`, `cook` или `savings`. Эти агенты импортируют общие сервисы, а не друг друга.

Общий `Product` определён в `foodai/models.py`. Ключ предложения состоит из зоны, витрины и SKU. Количества и цены считаются через `Decimal`; единицы `g`, `ml`, `pcs`. Неизвестный вес штуки не превращается в граммы. Пищевая ценность сохраняется с `nutrition_per` и `nutrition_source`; при неизвестной основе источник остаётся `unknown`.

Участник 1 отвечает за `agents/basket.py`, `services/catalog.py`, адаптеры импорта и подключение роутеров. Минимальные `services/address.py` и `services/pricing.py` нужны для самостоятельного запуска первого агента; это точки интеграции с адресным модулем участника 3 и калькуляторами участника 4. Рацион, рецепты, домашние запасы, замены с контролем КБЖУ и справочные значения питания остаются задачами остальных участников.

## Два сценария демонстрации

В Telegram пользователь вводит адрес, а ответы показывают название магазина,
фасовку на русском языке, количество упаковок и сумму. Внутренние zone/storefront/SKU
остаются в структурированных данных. Статус полноты исходного каталога сохраняется
в данных; в ответе перечисляются только отсутствующие позиции конкретной корзины.
Обычные сокращения «ул.», «д.», «корп.» распознаются для десяти известных домов;
другие дома не приравниваются к ним. По геопозиции явно показывается выбранный дом зоны.

Без ключа Groq локальный обработчик принимает простые фразы «Купи молоко и яйца»,
«литр молока», уточняет недостающие количества по очереди и сохраняет список между
сообщениями и перезапусками. Это ограниченный запасной режим, а не свободное понимание
языка: полноценный диалог выполняет Groq при `LLM_MODE=groq`.

1. `/start` → `msk_center` → «🛒 Где купить дешевле?» → «молоко 1 л, яйца 10 шт». Для контрольных тестовых предложений молоко 930 мл требует две упаковки; обычная Лавка даёт 300 ₽, Самокат 240 ₽. ВкусВилл без яиц остаётся неполным. Затем «Замени молоко на безлактозное» — яйца сохраняются, выполняется новый поиск.
2. Второй пользователь выбирает `msk_09` и «🍳 Что приготовить?» — видит заглушку и управляет своим адресом независимо. Первый пользователь меняет адрес через кнопку, выбирает `msk_02`, открывает корзину — прежние SKU сброшены. Запрос без количества вызывает уточнение. В каталоге с одним Ozon агент честно сравнивает только доступные данные.

Критерии B1–B6 и общий вход aiogram покрыты `tests/`. Для приёмки реального LLM повторите первый сценарий с `LLM_MODE=groq` и проверьте `tool_trace`: поиск, расчёт и сравнение выбирает модель. Одно только mock-демо не подтверждает живое function calling.

Официальные интерфейсы сверены с [Groq Local Tool Calling](https://console.groq.com/docs/tool-use/local-tool-calling) и [aiogram Router](https://docs.aiogram.dev/en/latest/dispatcher/router.html).


## Адрес и устойчивый черновик корзины

Адресные кнопки больше не предлагаются: пользователь вводит улицу и дом. Известные
адреса разрешаются локально, остальные — через Photon/OpenStreetMap с точной проверкой
улицы и дома, затем координаты проверяются по полигонам десяти зон. Неоднозначные,
не найденные и находящиеся вне зоны дома не подменяются ближайшим адресом.
Квартира, подъезд, этаж и домофон удаляются перед запросом к геокодеру. Результаты
кэшируются локально; запросы одного экземпляра приложения сериализуются с интервалом
не менее секунды. GEOCODER_URL позволяет заменить публичный сервер своим.
Публичный Photon подходит для небольшой демонстрации и не гарантирует доступность;
при росте нагрузки нужен собственный сервер или договор с провайдером.
[Условия и API Photon](https://github.com/komoot/photon#demo-server).
Если первые пять результатов не содержат точного дома, выполняется один резервный
поиск улицы и основного номера (до 50 результатов, без объединения дублей).
После него проверяются исходные улица, номер, корпус и строение; порядок номера
дома и корпуса сохраняется. Дома Московской области не переименовываются в Москву.
Совпадение основного номера с другим корпусом возвращает варианты для уточнения,
а не назначает зону. Кэш v3 не использует старые результаты с другой проверкой.
Поддерживаются присланные ссылки Google Maps с явными координатами в q/query:
центр карты ll не используется как точка дома. Для точки далеко от Москвы и точки
вне десяти полигонов выводятся разные объяснения. Геопозиции обрабатываются локально.
Каталоги остаются снимками для зон, а не подтверждением наличия и доставки в каждый дом.

Промежуточный draft сохраняет продукты и отдельно неизвестные количество/единицу.
Короткие ответы с количествами связываются с ним по порядку. Уточнение сорта сохраняет
известное количество и остальные продукты; отдельная единица pack означает число
упаковок/буханок, а не выдуманную массу штуки. Модель обновляет черновик инструментом;
её свободные сообщения не используются как подтверждение цены, наличия или доставки.
Вопросы о стоимости готовой корзины возвращают последний проверенный расчёт.

Базовые фразы «кило гречки», «молоко литр» и уточнение «килограмм гречки»
разбираются локально: килограмм сохраняется как 1000 g, литр — как 1000 ml.
Явное количество из текущего сообщения проверяется приложением даже при разборе
моделью. Штучный запрос листового салата означает число упаковок, поэтому фасовка
каталога в граммах не исключает салат из поиска. Масса отдельного листа не выводится.
Для базовых запросов круп и листового салата проверяется вид товара, а не только
похожесть названия. Мука, готовые блюда, детские каши и греческий йогурт не заменяют
гречневую крупу. Эта проверка действует в поиске, после переформулирования моделью
и при расчёте корзины. Отсутствующий подходящий продукт остаётся отсутствующим.
Сохранённые расчёты предыдущей версии правил не выдаются как новые результаты.
Поддержаны «пачка/пачки/пачек» и «упаковка/упаковки»; десятичная запятая в 1,5 л
остаётся частью количества. Для обычного запроса чипсов выбираются картофельные;
кола без сахара допускает обозначение Zero, но не другие напитки и обычную колу.
В коротком списке базовых продуктов учитывается цена целого требуемого количества.
Повторное идентичное обращение к локальному поиску использует уже полученные данные.
Разрешены основной поиск и одно переформулирование, до двух чтений деталей и до
трёх обращений к модели за сообщение. При незавершённом выборе корзина собирается
локально только для базовых запросов с явной проверкой вида товара и ограничений;
неизвестные виды и дополнительные неразобранные предпочтения не подменяются.

Предпочтения уточняются до расчёта: общий «салат» требует выбора листового салата
или готового блюда. «Хочу чипсы lays» меняет бренд прежней позиции, сохраняя её id,
количество и остальные продукты. Написания Lay's/Lay’s/lays/лейс/лэйс равнозначны.
Если нужного бренда нет, запрос остаётся в списке, а другой бренд предлагается
только после согласия пользователя. Недостающие позиции показываются с брендом
и количеством. Для колы, указанной в миллилитрах/литрах, сначала ищется упаковка
именно этого объёма. Набор маленьких банок вместо большой бутылки требует отдельного
согласия; при отказе фасовка сохраняется в неподобранных позициях. Ответы на
уточнения сохраняются вместе с сигнатурой продукта, бренда, количества и единицы;
изменение запроса требует нового согласия.

При HTTP 400 tool_use_failed для GPT-OSS допускается одна смена формата: модель возвращает действие и аргументы через strict JSON Schema, без native tools в этом запросе. Адаптер преобразует их в прежний интерфейс, контроллер повторно проверяет доступное действие, SKU и параметры. Другие HTTP 400 этим механизмом не маскируются; исходный диалог не изменяется.


## Экономия запросов и измерение токенов

Простые списки базовых продуктов с явными количествами разбираются локально. Свободные
формулировки, бренды и ограничения по-прежнему обрабатывает модель. Поиск по уже
сохранённым требованиям выполняется приложением, без отдельного обращения к LLM.
Для выбора SKU отправляется свежий компактный снимок требований и кандидатов, без
накопленной цепочки вызовов и чеков. Обычный простой список требует одного обращения
к модели, сложный — двух; ошибки и переформулирование могут потребовать дополнительных.
Вопрос о цене уже рассчитанной корзины не обращается к модели.

`LLM_USAGE_PATH` задаёт локальный JSONL-журнал. По умолчанию он расположен рядом с
пользовательской SQLite. Для каждого HTTP-ответа сохраняются статус, размер запроса,
случайный request_id и usage провайдера (prompt/completion/total/cached tokens), без
текстов, адресов и ключей. В `structured.usage` результата — сумма за сообщение.
Для ошибок провайдер не всегда сообщает расход: такие попытки помечены как
unmetered_http_calls, а не объявляются бесплатными. model_calls — число обращений к
адаптеру, http_calls включает его повторы.

Локальное сравнение с предыдущей версией на каталоге Ozon: корзина из двух товаров —
3 → 1 обращения, 16930 → 4897 байт; из трёх — 3 → 1 обращения, 19221 → 5854 байт.
Расчёты и выбранные предложения совпали. Измерены сериализованные messages + tools без общих параметров HTTP-запроса, не токены;
точный расход доступен только из usage. Сравнение выполнялось без платных/API-запросов.
